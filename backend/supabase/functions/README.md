# Supabase Edge Functions

The OAuth connection backend is implemented in:

- `oauth-start`: authenticated OnePost users begin a provider authorization flow. It validates the Supabase access token, creates short-lived one-use state, stores a server-encrypted PKCE verifier where supported, and returns an HTTPS authorization URL.
- `oauth-callback`: receives the provider redirect, atomically consumes the one-use state, exchanges the code on the server, discovers the authorized account(s), encrypts tokens with AES-GCM, writes accounts and credentials transactionally, and redirects to the OnePost app.

The functions support Instagram professional accounts, Facebook Pages, TikTok, YouTube channels, LinkedIn members, and X accounts. Provider credentials and user tokens are never returned to the mobile client.

## Deployment

Follow [`docs/oauth-deployment.md`](../../../docs/oauth-deployment.md) before deploying. In short:

1. Apply `migrations/002_oauth_connections.sql` after the initial schema.
2. Register the exact `oauth-callback` HTTPS URL in each provider developer app.
3. Configure provider credentials and an encryption key as Supabase Edge Function secrets.
4. Deploy `oauth-start` with JWT verification enabled and `oauth-callback` with JWT verification disabled. The callback instead requires an unexpired, single-use state generated by the authenticated start function.
5. Test each provider with its permitted developer/test accounts and scopes.

`SUPABASE_SERVICE_ROLE_KEY` and `OAUTH_ENCRYPTION_KEY` are server-only. Never put them in the Flutter app, APK, `.env`, or GitHub. Do not copy credentials into issues, chat, logs, or screenshots.

## Not included

Completing an account connection does not implement publishing. Provider-specific publish adapters, token refresh/revocation workers, durable job processing, webhook validation, and production monitoring are still release blockers. Some providers require app review or elevated access before real users can authorize the requested scopes.
